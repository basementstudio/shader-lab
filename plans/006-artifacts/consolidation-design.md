# Renderer consolidation design (plan 006)

Companion to [drift-inventory.md](./drift-inventory.md) (generated by
`generate-drift-inventory.ts`). All claims marked **[tested]** have a command
and output in the appendix.

## Summary of the current duplication

Two hand-maintained parallel trees:

- `src/renderer` + `src/fluid` (editor app): 86 files
- `packages/shader-lab-react/src/renderer` + `.../fluid` (published runtime): 87 files

Inventory classification (after normalizing import specifiers **and** biome
formatting, so only logic differences count):

| Class | Count | Meaning |
| --- | ---: | --- |
| IDENTICAL | 3 | byte-identical |
| IDENTICAL-MODULO-IMPORTS | 33 | < 10 normalized diff lines |
| DRIFTED | 27 | small real logic differences |
| DIVERGED | 20 | structurally different |
| SINGLE-SIDED | 7 | exists in one tree only |

Two systematic drift patterns dominate the DRIFTED class:

1. **Placeholder texture**: 22 package renderer files use
   `createPipelinePlaceholder()` (HalfFloat/RGBA/nearest placeholder that
   avoids a TSL pipeline recompile); the app versions still use bare
   `new THREE.Texture()`. The package is ahead of the app. **[tested]**
2. Small per-pass fixes that landed on one side only (e.g. `ink-pass.ts` is
   706 lines in the app vs 828 in the package; `pixel-trail-pass.ts` carries
   editor-only interaction recording).

## Q1 — Source of truth: the package

**Recommendation: `packages/shader-lab-react` is the source of truth.** No new
`shader-lab-core` package in the first migration.

- The package is published and already received quality fixes the app didn't
  (placeholder texture pattern, import hygiene) — it is the better copy for
  the shared logic.
- The repo already treats the package as the source of truth for one whole
  subtree: `src/fluid/runtime.ts` and `src/fluid/types.ts` are **5/8-line
  re-export shims over the package source** (see Q2). **[tested]**
- A separate core package adds a publish/versioning surface without solving
  anything the existing workspace dependency doesn't already solve.
- Editor-only modules (see Q4 dispositions) simply stay in `src/renderer` —
  package purity is not a goal; deduplication is.

## Q2 — Consumption mechanism: fluid-style source re-export shims

Three mechanisms were evaluated:

### (a) Import from built `dist/` via the package name — rejected

This is nominally today's mechanism, and the investigation found it is
**silently type-unsafe**:

- The app's only typed view of `@basementstudio/shader-lab` is the ambient
  declaration `src/types/basementstudio-shader-lab.d.ts`, which re-exports a
  hand-curated name list from `../../packages/shader-lab-react/dist/src/index`.
- That re-export does not actually bind the dist types: **every member of the
  ambient module resolves to `any`**. A probe file assigning the
  `ShaderLabComposition` component to a `number` type-checks cleanly.
  **[tested — probe A]**
- Because of `skipLibCheck: true`, the broken re-export never errors. Members
  missing from the curated list produce TS2305 even when present in dist
  (observed with a `PosterizePass` export during the pilot), and members
  present in the list are `any`.
- `next.config.ts` additionally aliases the package name to
  `./packages/shader-lab-react/dist/src/index.js` for both turbopack and
  webpack, so any **value** import requires a prior `bun run build:runtime`
  in the dev loop. Today the app has **zero value imports** of the package
  name — only `import type` (erased) — so `bun dev` currently works without
  a prior build. Migrating passes through this mechanism would break that.
  **[tested — import audit]**

### (b) Fluid-style relative source re-export — recommended

`src/fluid/runtime.ts` already does exactly this, in production today:

```ts
export {
  createShaderLabFluidRuntime,
  ShaderLabFluidRuntime,
} from "../../packages/shader-lab-react/src/fluid/runtime"
```

- Fully typed (real source module, no ambient `any` hole).
- No `build:runtime` needed in the dev loop (Next transpiles the workspace
  source it imports; proven by the existing fluid usage in `bun dev` and
  `bun run build`).
- Migration per file is mechanical: replace `src/renderer/<file>.ts` body
  with a re-export shim; every `@/renderer/<file>` importer keeps working
  unchanged.
- Keeping a shim (rather than deleting the file and rewriting importers)
  minimizes each migration diff and preserves the `@/renderer/*` module
  layout; the biome grit plugin that bans relative parent imports needs an
  exception for these shims (the fluid shims already establish the pattern).

### (c) `transpilePackages` + package-name imports — viable later, not first

Would give the canonical `@basementstudio/shader-lab` import path in app
code, but requires fixing the ambient-`any` problem first (pointing types at
source or deleting the ambient file) and reworking the `next.config.ts` dist
aliases. Worth revisiting after the shim migration lands; the shims can be
mechanically rewritten to package-name imports at that point.

**Independent of the migration, the ambient-`any` finding deserves its own
follow-up fix** — the editor currently has no type checking on any package
API it uses.

## Q3 — Type unification

`src/types/editor.ts` (534 lines) vs `packages/shader-lab-react/src/types/editor.ts`
(17 lines): **these are not two copies of one file** — the package version is
a deliberate adapter mapping its public `ShaderLab*` types onto the internal
names the renderer files expect (`LayerParameterValues`, `LayerCompositeMode`,
`MaskConfig`). **[tested — see appendix]**

Blocking differences for pass migration:

1. **`SceneConfig` does not exist in the package at all** (0 grep hits), but
   the app `PassNode` API references it (`updateSceneConfig`). Resolution: add
   a minimal structural `SceneConfig` (or the subset actually used by passes)
   to the package adapter. Only two files override `updateSceneConfig`:
   `text-pass.ts` (DIVERGED — stays split in Phase 3) and the app-only
   `scene-post-process.ts`, so the default no-op covers every migrated pass.
2. Package `MaskConfig.mode/source` are `string`; app uses union types.
   Compatible in the app→package direction (unions are assignable to string),
   so passes typed against the package adapter accept app values.
3. `EditorLayer` (app) vs `ShaderLabLayerConfig` (package) differ, but passes
   don't consume whole layer objects — only `LayerParameterValues` — so this
   does not block pass migration. It blocks unifying `contracts.ts` /
   `pipeline-manager.ts` (DIVERGED anyway, see Q4).

Conclusion: converging the two `types/editor.ts` files is **not** required;
keep the adapter, extend it with `SceneConfig`.

## Q4 — Migration order

**Phase 0 (prerequisite, one PR): reconcile the base class.**
The app `PassNode` has three members the package's lacks — `updateSceneConfig`,
`updateOutputCropAspectRatio`, `prepareForExportFrame` — and the app
pipeline-manager calls the first two on **every pass every frame** and awaits
the third during export. **[tested — call-site grep]** Port them into the
package `PassNode` as the default no-ops they are in the app, add the adapter
`SceneConfig` type, then replace `src/renderer/pass-node.ts` with a source
re-export shim. This puts every app pass in the *same class hierarchy* as
package passes (protected/private members make TS class assignability
nominal — two parallel `PassNode` declarations can never satisfy each other).
Behavior note: the shim adopts the package's `createPipelinePlaceholder()`
constructor path for all app passes — this is the package's recompile-avoidance
improvement and needs one manual render check of each pass category.
`blend-modes.ts` (IDENTICAL) shims in the same PR.

**Phase 1 (mechanical batch): IDENTICAL + IDENTICAL-MODULO-IMPORTS (36 files).**
Replace each app copy with a shim. Includes most of `shaders/tsl/`
(29 utility files), `ascii-atlas.ts`, `dither-textures.ts`, `bloom-pass.ts`,
`pattern-pass.ts`, `plotter-pass.ts`, `posterize-pass.ts`,
`threshold-pass.ts`, `live-pass.ts`, `custom-shader-runtime.ts`. One
changeset; manual render check per migrated pass type.

**Phase 2 (per-file reconciliation): DRIFTED (27 files).**
For each: diff, port app-only behavior into the package copy (the app is the
editor of record for behavior; the package for hygiene), then shim. Batch by
size — the ~10–25-line files first (crt, smear, circuit-bent, fluted-glass,
pixel-sorting, directional-blur, chromatic-aberration, displacement-map,
edge-detect, pixelation, voxel, gradient, halftone, ascii, dithering,
particle-grid, slice, custom-shader-pass, media-pass), then the structural
ones (`pixel-trail-pass.ts` — editor interaction recording must layer over a
shared core, `fluid-pass.ts`).

**Phase 3: DIVERGED (20 files) — mostly stay split, by design.**
`media-texture.ts` (editor adds video playback modes + SVG rasterization over
the package's 66-line loader), `contracts.ts`, `pipeline-manager.ts`,
`create-webgpu-renderer.ts`, `ink-pass.ts`, `magnify-lens-pass.ts`,
`text-pass.ts`, `pattern-atlas.ts`, `tonemapping.ts` and the noise variants:
each needs an explicit keep-split / extract-core decision in its own review.
No shims here in the first migration.

**SINGLE-SIDED files keep their homes**: app-only `pass-node-factory.ts`,
`project-clock.ts`, `scene-post-process.ts`; package-only `asset-url.ts`,
`create-headless-renderer.ts`, `text-fonts.ts`, `fluid/utils.ts`.

## Q5 — Guardrail against re-duplication

Add `scripts/check-renderer-dedup.mjs` to CI (after lint) with the manifest of
migrated files. For each entry it asserts `src/renderer/<file>` is either
absent or a re-export shim (≤ 10 lines, single `export ... from` statement
into `packages/shader-lab-react/src/...`). Fails with the file list otherwise.
The manifest grows with each migration phase; the script lands with Phase 0.

## Pilot outcome (plan step 3 — STOP condition invoked)

Attempted the strictly in-scope pilot with `posterize-pass.ts` (smallest
normalized diff among factory-imported passes, import-order-only difference):
exported `PosterizePass` from `packages/shader-lab-react/src/index.ts`, built,
pointed `pass-node-factory.ts` at `@basementstudio/shader-lab`, deleted the
app copy. Findings:

1. `tsc` first fails with TS2305 because the ambient
   `src/types/basementstudio-shader-lab.d.ts` — not the package's dist
   types — defines what the app can import. After adding `PosterizePass`
   there, `tsc` passes — **vacuously**, because every ambient member is
   `any` (probe A). The green typecheck proves nothing.
2. At runtime the app pipeline-manager calls `updateSceneConfig` /
   `updateOutputCropAspectRatio` on every pass every frame; the package
   `PassNode` has neither **[tested — dist .d.ts + call-site grep]**, so a
   package-sourced pass throws `TypeError` as soon as a posterize layer
   renders. The type hole in (1) is exactly why tsc cannot catch this.
3. A properly-typed pilot needs the two `PassNode` declarations to be one
   class (nominal assignability), i.e. Phase 0 above — which the plan
   explicitly rules out as a pilot side-effect ("type unification is a design
   output"). Per the plan's STOP condition, the pilot changes were reverted;
   steps 1–2 are delivered with this report.

**Recommended follow-up plan**: Phase 0 as its own plan/PR (package `PassNode`
reconciliation + `pass-node.ts`/`blend-modes.ts` shims + dedup guardrail
script + changeset), then Phase 1 as a second PR. Phase 0 supersedes the
one-pass pilot: after it, migrating `posterize-pass.ts` is a two-line shim.

`bun dev` note (design question 2 evidence): the app currently needs
`bun run build:runtime` only for the *runtime* of package-name value imports
(none exist today) — not for types (ambient `any`) and not for fluid (source
re-export). The recommended mechanism keeps the dev loop build-free.
